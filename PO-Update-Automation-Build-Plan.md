2. ~~Build the intake job as polling (confirmed sufficient at 10–20 emails/week — no webhook needed), pulling new messages + attachments from a designated folder every 15–30 minutes.~~ **BUILT 2026-09-14.** `graph_client.py` (the four-method interface plus a mock and a real client), `poller.py` (the job and the content-addressed store) and `extract_pending.py` (the extraction driver). 87 checks in `test_poller.py`, offline throughout.

   **"A designated folder" was never resolved, and is deliberately not implemented.** `Mail.Read` is mailbox-level, no folder was ever named, and the mailbox is dedicated to this pipeline — so everything in it is in scope. The folder each message came from is **recorded** (`messages.folder_id`, Graph's opaque `parentFolderId`), so a folder rule can be added later from stored rows rather than by re-reading the mailbox. Resolving that id to a display name would need a fifth Graph call, which the interface does not have.

   **The interface is the whole Graph surface, and it is enforced twice.** Four methods on an ABC; an AST scan fails the build on any HTTP verb but GET, any write-shaped or out-of-scope Graph path, and any `os.environ` read. The scan reads code rather than text — `graph_client`'s docstring names `/mailFolders` and `os.environ` while explaining why neither is used, and a substring search cannot tell a prohibition from a violation — and it **verifies itself** against a synthetic violating module, per §8 lesson 18.

   **The ingest → extraction seam, which the plan never named.** The poller writes bytes to a content-addressed store (filename = SHA-256 = the `attachments` primary key, so store and database agree by construction) and records the path in `stored_uri`. `ingest_shipment` already takes paths and is **unchanged**. `extract_pending.py` is a separate command that reads `messages` rows with `extracted_at IS NULL` and calls it. Two commands, never chained: chained, a parser bug costs a re-download and the re-extraction cost decision gets made implicitly by whoever ran the poll. `--all` re-opens the whole set, which is the actual requirement — a parser change re-runnable over everything stored without touching Graph.

   **Watermark** (`poll_state`): `receivedDateTime` with a five-minute overlap, never a bare `>`, because two messages in the same second or any clock skew lose mail silently on a strict comparison. It advances to the newest message stored **before the earliest failure** — advancing past a failure retires the shipment, never advancing freezes intake behind one bad message. Idempotency (`graph_message_id`, with `internetMessageId` stored alongside since the two survive different things) makes the re-read free.

   **Verified end to end** through `alembic upgrade head` against the mock: 7 messages, 9 joins, **8 files on disk** — the re-forward deduped — and a second poll storing nothing.

   **The first live poll is a chosen one, not an accident.** Cold start was unbounded: with no watermark the window opened at `EPOCH` and the run pulled the entire mailbox. That is the right library default — silently skipping history is the worse error — but a poor thing to find out by doing it, and this mailbox is being seeded with forwarded historical slips. **The CLI now refuses a cold start without an explicit choice** (`--since`, `--from-beginning`, or `--dry-run`) and exits 2; every later poll has a watermark and needs no flag.

   - **`--since`** overrides the window entirely, watermark included — how a first run is made small, and how a known period is re-read. Safe because re-reading is deduped, the same property the overlap relies on. A naive value is read as UTC; local would shift the window by the machine's offset.
   - **`--max-messages`** caps one run. Oldest-first, so a cap takes the oldest N and the next run continues; the run is flagged `truncated`, because *"I stopped early"* and *"that was everything"* must not look alike.
   - **`--dry-run`** lists what it WOULD store and writes nothing — no rows, no bytes, and deliberately not `last_polled_at`, so a dry run cannot masquerade as a poll in the monitoring signal. It fetches attachment **metadata only**; a test proves `get_attachment` is called zero times. Reports sender, subject, filenames, sizes and total bytes. Same shape as the auth probe: find out what is true before acting on it.

   **A capped run stores one fewer than its cap on the NEXT run**, because that window opens at the watermark minus the overlap and re-reads its own boundary message. That is the overlap working, not a defect — a capped run that skipped its boundary would leave exactly the gap a bare `>` produces — and the test asserts the interaction rather than a number that hides it.

### What Phase 2 never anticipated and got built anyway

The plan's item 2 was one sentence. These are the pieces it turned out to need, none of them a line item:

- **A four-method Graph interface** (`list_messages` / `get_message` / `list_attachments` / `get_attachment`) as the entire Graph surface, enforced by an AST scan that fails on any HTTP verb but GET and verifies itself against a synthetic violating module.
- **Two implementations** selected by `GRAPH_CLIENT` with no code change — a mock serving the five real vendors in realistic envelopes, and a certificate-auth real client.
- **`scripts/probe_graph_auth.py`**, which found a missing certificate on its first run and converted mailbox scoping from asserted to observed.
- **`config.GraphConfig`** — one `.env` loader, strict client selection with no default, and a certificate-pair check that catches "the cert uploaded to Entra is not this key's".
- **A content-addressed attachment store**, filename = SHA-256 = the `attachments` primary key, so the store and the database agree by construction.
- **The ingest → extraction seam.** `ingest_shipment` is unchanged; `extract_pending.py` re-runs extraction over stored rows without touching Graph, which is what makes a parser change cheap.
- **Cost instrumentation** (migration 0006) — per shipment and per source document, after the first live run showed the figure was being computed and discarded.

### Deferred by evidence, not by omission

**Multi-shipment-per-email.** One email carrying several vendors' shipments produces one shipment; the others' lines are parsed as cross-checks and not proposed. That is visible on `shipment_sources` rows and priced per document, but not supported.

**It is deferred because the live mail does not need it.** The only message mixing vendors was `2026-09-14 20:31:08`, subject **"Shipment updates"** — a seeded test message, the only one without a `Fw:` prefix and the only one predating the historical forwards. **Paula's five real forwards each carry exactly one vendor.** One shipment per email is what real vendor mail looks like, which is what `ingest_shipment` already assumes.

Build it when a real multi-vendor email appears, not before — and when it does, the economics are already measured rather than guessed: a cross-check costs a full extraction, so proposing its lines is nearly free.

## Phase 3 — Review/approval + write-back (~4–6 days)

1. ~~Build the review step — recommend starting with the **email-approval** version (a digest email with an approve link) rather than a full dashboard~~ **REVISED 2026-08-24 — an approve link is no longer sufficient.** The recommendation assumed the review step only had to *capture consent*. It has to **collect a value**: Paula supplies the receipt date herself (§6.1), and a link cannot carry a date she has not typed. So v1 needs at minimum a **small form**, not a mailto or a one-click URL. Two design points that follow, both learned rather than assumed:
   - **The date field must be OPTIONAL.** Quantity is knowable from the packing slip the moment it arrives; the receipt date often is not, because it waits on the forwarder. Requiring a date to approve a quantity would stall the common case behind the slower one — so the form must support approving quantity alone, which is exactly what `to_netsuite_fields(include_dates=False)` already exists for.
   - **`custcol_override_expected_receipt` must be set only when a date is actually written.** Setting the override flag on a quantity-only approval would assert an override with nothing behind it.

   A full dashboard remains a later upgrade; the change is that the *floor* for v1 is a form, not a link.
2. Wire the approval action to the NetSuite write-back built in Phase 1.

   **ACCEPTANCE CRITERION — the review UI must record a human verdict on EVERY line it shows, including lines accepted unchanged.** Not a nice-to-have, and easy to miss because the natural implementation only writes a row when Paula changes something. If verdicts are recorded only on disagreement, the calibration corpus has **no negatives**: the base rate is unknowable, and `needs_review` — which currently fires on 100% of documents and is therefore useless for triage — can never be calibrated. The columns exist (`human_verdict`, `verdict_by`, `verdict_at` on `proposed_changes`, surfaced by `v_calibration`); the UI has to fill them in for the accept case too. Getting this wrong is not visible until someone tries to calibrate months later and finds one half of the data missing.

   **Now measured, and the case is stronger than when this was written:** on the real corpus `needs_review` fires on **19 of the 29 correctly matched lines**. The flags are honest — the extractor genuinely inferred those values from block recap rows and carried-forward headers, and said so — but at two thirds of correct work they are unselective, and a reviewer will learn to ignore them within about a week. Those 19 are the first calibration rows with a **target line attached**, so they are exactly the corpus this criterion exists to build.

   **Also for whoever builds the screen:** `ns_line_is_open` and `ns_item_internal_id` describe the *matched* line, so when change 5 chooses no target they are NULL and the per-line open state lives on `candidate_lines` instead. Open state therefore comes from two places depending on outcome. That is deliberate — a copy on the row would be a second source of truth for something change 5 explicitly refused to decide — not an oversight.
   **ALSO REQUIRED — an assignment group must be presented AS A GROUP, not as independent rows.** When a slip splits one size across transport-mode recap rows, `NEEDS_ASSIGNMENT` produces N rows sharing N candidate lines, and **assigning one member constrains the others**: give `By Sea` line 5 and line 5 is no longer available to `By UPS`. Rendering them as separate rows with separate dropdowns invites a double-assignment the database will then reject — `ux_proposed_changes_one_line_per_shipment` refuses two changes targeting one line, so the UI would be offering a choice that cannot be saved.

   Concretely, the screen needs: the group's rows together, each with its recap label and quantity; the shared candidate lines once rather than repeated per row; and remaining choices narrowing as each assignment is made. The grouping key is `(shipment_po_id, key_style, key_color, key_size)` — i.e. the canonical key **without** `key_recap_label`, which is exactly `matcher._sibling_key`. This is the first review-screen requirement with cross-row state; everything before it was per-row.
3. Error handling: what happens if NetSuite rejects a write (e.g., closed PO, permission error) — should surface clearly, not fail silently.
4. Confirmation notification back to Paula (and Kiko) on success/failure.

**Exit criteria:** end-to-end flow works against sandbox — email in, review link out, approval in, NetSuite sandbox PO updated, confirmation out.

## Phase 4 — Hardening & production cutover (~3–5 days)

1. Run against a backlog of real historical vendor emails (if available) to shake out edge cases beyond the one sample we've tested.
2. **NEW — pre-cutover verification: does anything downstream fire on a write?** Every live NetSuite test so far has been write-verify-**revert**, and reverting within seconds is precisely what stops a downstream consumer from ever seeing the change. So the write path is proven while its **side effects are entirely unobserved** — a client-side script on the PO form, a workflow, the RepSpark feed, a notification to someone. The first shipment whose change is **left in place** is the first opportunity to check, so check it deliberately rather than discovering it: leave one real approved change standing, then confirm with Paula and whoever owns the NetSuite customizations whether the expected downstream effects occurred. Related known asymmetry: a REST PATCH does not run client-side form scripts, so a UI save and an API save are not necessarily equivalent (architecture doc §6).
3. **NEW — re-verify the tranId rule against PRODUCTION.** Sandbox is 100% conforming across 1,659 POs, but the Allow Override and Use Subsidiary / Use Location checkboxes were never actually read, and the two accounts have already been shown to differ elsewhere. Run the same survey there — every PO tranId against `^PO\d{7}$` — and report any non-conforming value before the first production write. Cheap, read-only, and it is the difference between "the convention holds" and "the convention held in sandbox".
4. **NEW — re-verify colour resolution against PRODUCTION data.** The two accounts provably disagree about the colour list, in **both** directions: the production export has 620 values with curated long names in `Name`, sandbox has 589 with the 3-letter code there, and sandbox holds at least one value the export lacks (id 576 `TAYLOR WHITNEY CABERNET`/`TWC`). Change 7 resolves colour through `custitem_psgss_product_color_desc` on the child item precisely because that field is verified in sandbox — but it has **never been read in production**. Before cutover, check three things there: that the item field is populated on items appearing on open POs (it is 2,390 of 2,393 in sandbox), that no single PO carries two colours whose names collide (zero of 133 in sandbox), and whether production's curated list `Name` would be the better source now that it exists. Do it as a read-only survey, not as a code change.
5. **NEW — re-verify the SIZE VOCABULARY against PRODUCTION.** `netsuite_size_list.json` is a **sandbox snapshot** — `1321665-sb2`, 46 values, fetched 2026-09-02 — and it is read at *runtime* by `size_vocabulary.size_labels()`, not fetched live. It is what the size-header detector recognises as a size at all, and what `extraction_schema.enforce_size_composition` checks a composed two-axis size against before accepting it. Refresh it against production (`python size_vocabulary.py --refresh`, which needs `Setup > Custom Lists` View on the production role) and **diff it against the sandbox file before trusting either**.

    **What happens if this is skipped: nothing visible.** If production's list differs, a size header goes unrecognised or a composed size like `30-32` fails its vocabulary check — and the line is dropped or flagged, with **no error anywhere**, because a size that is not in the vocabulary is indistinguishable from a cell that was never a size. The tool reports fewer matched lines and gives no reason. The sandbox list has already been shown to be an unreliable proxy for production once, on colours (item 4), and there is no reason sizes would be the exception.

    **These three items — 3 (tranId), 4 (colour resolution) and 5 (the size vocabulary) — are one problem, and naming it once is the point.** Each is a **sandbox-derived fact the pipeline treats as settled**: a numbering convention measured across 1,659 sandbox POs, a colour source field verified on 2,390 sandbox items, a size list captured from sandbox on one day in September. None is read from production. None is re-checked at runtime. And **all three fail the same way if production disagrees — silently, as a non-match rather than an error**, because every one of them is an input to *matching*, and matching's failure mode is producing fewer rows, not raising.

    That is the shape to recognise: **a fact learned from sandbox, baked into matching, with no runtime check that it still holds.** When a fourth appears — and it will, every time the pipeline learns something new about this account's data — it belongs on this list, and the test is a single question: *if production disagreed with this, would anything say so?* If the answer is no, it is one of these. Named as a general shape in RUNBOOK §8 lesson 16.

6. **Build the production NetSuite Integration record and role by following `NETSUITE-M2M-SETUP.md` Steps 1–5 against production** — not by copying the sandbox role from memory or by reading its permission screen. That document now carries the **seven**-permission set with the subtab named for each, and the two that are not where their names suggest (`Custom Lists` on **Setup**, `SuiteAnalytics Workbook` on **Reports**). It previously listed five and said not to add more — which would have produced a role that authenticates, passes the write-back test, and then fails on every real vendor document. **Verify the finished role with Setup > Users/Roles > Show Role Differences** (Base Role = `Administrator`, Compare To = the new role, Only Show Differences, export CSV) rather than by reading the role editor — it shows *actual* saved state, and a permission that reads as set and was never saved is how this project lost five probe cycles (RUNBOOK §8 lesson 1). **Then run `test_phase1_writeback.py` against production** and date the result in RUNBOOK §6, per the standing rule that any permission change re-runs that test. ~~**Least-privilege check while doing it:** test whether **View** suffices for `Reports > SuiteAnalytics Workbook` and downgrade if it does.~~ **That check is CLOSED, 2026-09-09 — no action at cutover.** `Reports > SuiteAnalytics Workbook` offers **only `Edit`** in the role editor's level dropdown; `View` is not an option, so `Edit` is the minimum NetSuite permits and not a compromise to unwind. Oracle's documentation says *"set the access to Edit"* rather than describing a range. Grant it at `Edit` on the production role and move on.
7. **Lock `audit_log` down to append-only at the database, not by convention.** The application never updates or deletes those rows, but nothing stops it — and an audit trail that *can* be rewritten is worth less than one that cannot. Create a database role for the application with `INSERT` and `SELECT` on `audit_log` and **no `UPDATE` or `DELETE`**, and connect as it rather than as the schema owner. Azure SQL: a contained user with explicit `GRANT`/`DENY`. Worth doing at cutover rather than later, because retrofitting it means finding out whether anything had quietly come to depend on the ability. (Recorded in schema rationale §7; this is the phase that has to act on it.)
8. Basic monitoring/alerting (e.g., "intake job hasn't run in X hours," "NetSuite write failed") so silent failures don't sit unnoticed.
9. Short handoff doc for Paula (how to use the review/approval step) and for whoever maintains it after Kiko.

**Exit criteria:** running unattended against production for a real shipment, successfully, with Paula using the actual review step (not Kiko testing it).
